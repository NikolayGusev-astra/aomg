# ADR-0004: Политика перезапуска stdio-детей — circuit breaker вместо бесконечного респауна

Статус: accepted, 2026-09-30

## Контекст

Пользовательский баг-репорт из сессии 20260930_100646_31e2ee, дословно:
«каждые 30 секунд краш».

Корневая причина найдена в логе установленной сборки
(`%LOCALAPPDATA%\Programs\AOMG\logs\weather.log`):

```
===== spawn 2026-09-30 16:54:37: uvx --from mcp-server-weather mcp-server-weather
...
ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x,
  where FastMCP was renamed to MCPServer ...
```

`uvx mcp-server-weather` тянет mcp 2.x → ребёнок умирает на `initialize` →
`watchdog.py` видит `not alive()` → `supervisor.restart()` **безусловно** →
через 30 секунд ровно то же самое. В логе шесть маркеров `===== spawn` за
четыре минуты. `uvx` при этом перекачивает/пересобирает окружение по кругу.

Реальная проблема — не «краш», а **отсутствие политики**: у AOMG нет ответа
на вопрос «этот сервер только что упал третий раз подряд — что делать?».
Единственное, что предлагалось (незакоммиченный `fails`/`MAX_FAILS` в
`watchdog.py`), меняет **текст статуса** и продолжает рестартовать. Это
косметика: порты плодятся, `uvx` крутится, пользователь видит «не отвечает
после 3 попыток» и не понимает, что рестарты идут четвёртым.

Дополнительно: в `watchdog.py:83` `supervisor.restart(name)` вызывается
**до** записи состояния, и нигде не логируется, *почему* ребёнок умер —
хотя `supervisor.last_error(name)` (хвост лога) существует и точно называет
причину.

## Решение

**Restart-политика живёт в `Supervisor` (владелец процесса), а не в
`watchdog` (наблюдатель).** Watchdog только сообщает факт.

### Симптомы, которые различаются

| Факт | Смысл |
|---|---|
| ребёнок умер, прошло < backoff | рестарт, состояние `reconnecting` |
| ребёнок умер, backoff не прошёл | **не трогаем**, состояние `reconnecting` + время до следующей попытки |
| ребёнок умер, `fails >= MAX_FAILS` | **разомкнутый автомат**: `down`, авторестарт прекращён |
| ручной рестарт из панели | счётчик сброшен, цепь замкнута, один авторестарт |
| `probe()` вернул `ok` | счётчик сброшен (ожил) |

### Параметры

```python
RESTART_BACKOFF = (0, 5, 15, 30, 60)   # секунды между попытками
MAX_FAILS = 3                          # после — разомкнуть, не рестарт
```

Экспоненциальный backoff с потолком 60 с. Первый рестарт — сразу (0 с):
для нормального падения (ребёнок убит извне) пользователь не ждёт.

### Диагностика вместо тишины

`ManagedServer` при старте пишет в лог маркер `===== spawn` уже; дополнительно
`Supervisor` при размыкании автомата пишет в лог сервера и в `Health.error`:

```
не отвечает: 3 попытки рестарта, авторестарт остановлен.
<хвост лога: ModuleNotFoundError: No module named 'mcp.server.fastmcp' …>
```

То есть панель и лог прямо называют причину — «мёртвый uvx-пакет», а не
абстрактное «не отвечает».

### Инвариант (проверяется тестом)

- **I1.** Число фактических `Popen` за 5 минут для одного упавшего сервера
  ≤ `MAX_FAILS + 1`. Рестарт-цикл конечен.
- **I2.** `probe() == ok` сбрасывает цепь: после успеха сервер снова
  получает полный запас попыток.
- **I3.** `api_restart` (панель) обнуляет счётчик и размыкает автомат —
  пользователь может починить команду и перезапустить без правки конфига.
- **I4.** Для HTTP-серверов (нет процесса) политика не применяется: там
  причина в сети, и AOMG не перезапускает то, что не перезапускается.

## Альтернативы, отвергнутые

- **Бесконечный рестарт с фиксированным интервалом** (текущее поведение) —
  антипаттерн, зафиксирован в логе: 6 спавнов за 4 минуты.
- **Только менять текст статуса** (предложенный в сессии фикс) — проблема
  в поведении, а не в формулировке; пользователь всё равно получает краши.
- **Перезапуск с выводом интерактивного запроса** («сервер упал, уточните
  команду?») в лог — для трей-приложения без окна консоли это
  непроходимо; к тому же причина (mcp 2.x) в логе уже есть.
- **Проверять `command` на существование до спавна** (мёртвый `C:/tools/
  corp-mcp.exe`) — полезно, но это ловит только один из классов отказа;
  `uvx`-пакет, падающий на импорте, существует. Делается как
  дополнительная проверка, circuit breaker покрывает остальное.
- **Перезапуск по расписанию (каждую минуту «просто попробовать ещё»)**
  тише для пользователя, но прячет поломку и всё равно крутит пакеты.

## Следствия

- `watchdog.py` теряет `fails`/`MAX_FAILS` — его роль сужается до
  «сообщить супервизору факт смерти и записать probe-результат».
- Появляется честный статус `down` с причиной — ровно тот, который
  пользователь просил («почему вообще падение то»).
- Тест на I1 — параметрический, без сети: подменяем `Popen` счётчиком.
- Приложение перестаёт «стрелять» в лог; `logs/<name>.log` остаётся
  диагностикой, а не потоком мусора.
